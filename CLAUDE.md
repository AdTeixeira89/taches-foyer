# Family Play : consignes pour Claude Code

Application familiale (tâches, calendrier, points, défis, bonus, roulette) pour un couple et leur fille.
Un seul fichier autonome : `index.html` (HTML, CSS et JavaScript, sans build ni dépendance), plus le logo (`logo.svg`, `icon-192.png`, `icon-512.png`, `apple-touch-icon.png`) et `manifest.json`.
La section « Idées » (avec dictée vocale) a été retirée de l'interface à la demande de la famille : la collection `ideas` reste dans les données et n'est jamais effacée.

## Règles à respecter

- Application **totalement indépendante** de toute application de budget : données et interface propres.
- **Ne supprimer aucune donnée ni fonction existante.** Les nouveaux champs doivent être facultatifs (les anciennes données restent valides).
- Ne pas changer les règles de jeu sans accord explicite : points par difficulté (1, 2, 3, 5), points attribués une seule fois par personne et par tâche (une tâche peut avoir plusieurs participants, chacun reçoit les points complets, accord explicite de la famille), aucun point jamais retiré, classement bienveillant, jokers (un de chaque par semaine, échange avec accord), roulette (5 segments égaux, un ticket tous les 10 points, un tour par semaine et par personne).
- Ne pas simuler une sauvegarde ou une synchronisation. Ne jamais mettre de fausses récompenses dans les données réelles.
- Interface en français, sobre et lisible sur téléphone, tablette et ordinateur. Animations et sons désactivables. Les sons (`sfx()`, table `SFX`, synthèse WebAudio, aucun fichier) sont activés par défaut tant que la personne n'a pas choisi dans les Réglages (`ui.fx.chosen`).
- Échapper tout texte affiché (`esc()`), car les données sont partagées entre plusieurs personnes.

## Données

- Mode **partagé** : la page publiée sur claude.ai utilise `window.claude.use('db')` (collections `tasks`, `ideas` (conservée, plus affichée), `events`, `points`, `weeks`, `pacts`, `jokers`, `spins`, `missions` et le document `settings/family`).
- Liste de courses : collection `courses` (`{name, aisle, done, archived, times, createdAt, by, doneAt, doneBy}`), jamais effacée par « Vider le panier » (archivage). Le drive (`ui.drive`, adresse avec `{produit}`, https seulement) est un réglage d'appareil. Repas de la semaine : collection `repas` (`{date, slot: 'midi'|'soir', name, items, by, at}`, id = `date_slot`), affichage midi / soir / les deux (`ui.mealSlots`), ingrédients envoyés vers `courses` par `shopAdd`. Mode claude.ai : mêmes collections dans la base de la page.
- Membres supplémentaires : liste facultative `members` du document `settings/family` (`{id, name, avatar, on}`, 5 au plus, identifiant `m…`, couleur fixée par la position dans la liste). On les masque (`on: false`), on ne les supprime jamais. Les points, tâches et événements les désignent par leur identifiant, comme pour `a`, `b`, `c`.
- Prénoms de départ : noms de démonstration (`Parent 1`, `Parent 2`, `Enfant`), jamais de vrais prénoms dans le code ; chaque famille saisit les siens (`settings/family.names`).
- Codes personnels (mode Firebase seulement) : document `settings/codes` = `{admin, codes: {<profil>: 'ABC123'}}` (6 caractères). Créé avec le foyer (le créateur = profil `a` = organisateur) ou activé dans les Réglages pour un ancien foyer. Tant qu'il n'existe pas, le choix libre du profil reste. Une fois présent, un appareil entre un code (jointure ou écran `#gate`) et reste relié à ce profil (`ui.lock`, préférences de l'appareil) : pas de changement de profil dans l'app, `meOf()` renvoie le profil relié. Seul l'organisateur voit tous les codes. Verrouillage de confort dans l'app, pas une sécurité forte (la base ne distingue pas les membres). Mode claude.ai et mode local : inchangés.
- Notifications push (mode Firebase seulement) : le téléphone enregistre son jeton sous `foyers/<code>/devices/<appareil>` (`token`, `who`, `updatedAt`, écriture seule d'après les règles). Les Cloud Functions de `functions/` (région `europe-west1`) lisent ces jetons et envoient via FCM quand une tâche, un joker, un événement ou une semaine est écrit ; la logique « qui prévenir » est dans `functions/notify.js` (testée). Champ facultatif `owners` (liste d'identifiants, plusieurs participants ; `owner` reste le premier, pour les anciennes données). Champ facultatif `by` (profil de l'auteur) sur les tâches et événements créés, pour ne pas notifier celui qui agit. Tâche terminée : champ facultatif `doneBy` (profil qui a validé, écrit par `completeTask`) ; `planDone` prévient tous les autres (`kind: 'done'`, vibration), l'app ouverte joue `sfx('bravo')` (`sfx('ding')` pour les autres messages, d'après `data.kind`). Une tâche créée (récemment, avec `by` et `createdAt`) prévient tous les autres membres ; son responsable reçoit un seul message, celui qui lui est destiné ; une tâche confiée plus tard prévient seulement le nouveau responsable. Tâche en retard : la fonction planifiée `sendOverdue` (chaque jour à 9 h, `collectionGroup('tasks')` sur `due`, index `firestore.indexes.json`) prévient les responsables (tous si « à prendre ») une seule fois par date limite (`reminderLog`, 7 jours au plus) ; le lien `?retard=<tâche>` ouvre la question « fait (par qui) ou repousser » (`lateSheet`), également proposée sur l'accueil (« À confirmer »). Veille d'un événement : la fonction planifiée `sendEventReminders` (chaque jour à 18 h, fuseau `TIMEZONE` de `functions/notify.js`, `collectionGroup('events')` sur `date`) prévient la personne concernée ou toute la famille, une seule fois (`reminderLog`). Rappel d'une tâche : champ facultatif `remindAt` (millisecondes, heure choisie dans le fuseau de l'appareil), proposé seulement en mode Firebase avec notifications ; la fonction planifiée `sendReminders` (chaque minute, `collectionGroup('tasks')`, index `firestore.indexes.json`) envoie au responsable (à tous si « à prendre ») et note chaque envoi dans `foyers/<code>/reminderLog` pour qu'un rappel ne parte qu'une fois. La clé publique est `FCM_VAPID_KEY` dans `index.html` ; à `null`, aucune option de notification n'apparaît.
- Déploiement des fonctions et des règles : workflow `.github/workflows/firebase-deploy.yml`, secret GitHub `FIREBASE_SERVICE_ACCOUNT` (clé JSON d'un compte de service). Jamais de clé ni de secret dans le dépôt.
- Mode **Firebase** (GitHub Pages, https://adteixeira89.github.io/taches-foyer/) : quand `FIREBASE_CONFIG` est renseigné, mêmes collections sous `foyers/<code famille>/` dans Firestore (connexion anonyme, code de 12 caractères gardé dans `localStorage` sous `famille.firebase.code`). Règles dans `firestore.rules`.
- Mode **local** (`FIREBASE_CONFIG` à `null`, fichier ouvert directement) : repli sur `localStorage`, clés `famille.local.*`. Les données ne sont alors pas partagées.
- Les bases claude.ai et Firebase sont distinctes. Après toute modification du code, pousser sur `main` (GitHub Pages) et republier la page claude.ai.

## Vérifier avant de livrer

- Le script s'exécute sans erreur (vérifier la syntaxe, ouvrir la page).
- Créer, modifier, terminer, masquer une tâche ; points attribués une seule fois ; roulette un seul tour par semaine ; anciennes données toujours lisibles.
- Contrôler l'affichage sur petit écran et en mode sombre.
